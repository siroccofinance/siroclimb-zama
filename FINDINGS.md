# Findings

Issues found while building and running Siroclimb on Sepolia and on the FHEVM mock, and how each one
was fixed. The on-chain battery reports are at the end.

## Integration findings

| # | Finding | Where | Fix |
| - | ------- | ----- | --- |
| F1 | The game contract came out at 26.3 KB, over the 24 KB code size limit. | Contracts | The run rules moved into `ClimbLadder`, a stateless contract the game reads (long and short multipliers on the oracle path). The game is now 23.2 KB and the rules can be audited alone. |
| F2 | Concurrent user decryptions on the FHEVM mock failed with "Parse event … in backward order": the mock coprocessor's log cursor is not reentrant. | Tests | Balance decryptions in the tests run one after the other (`balances()` helper). |
| F3 | The hardhat FHEVM plugin raised its own assertion ("Fhevm assertion failed") instead of the revert reason for a reverted *send* to a non-FHE contract. | Tests | That expectation uses `staticCall`, which returns the custom error. |
| F4 | A Sepolia deployer key shared with another live project raced it for nonces (`nonce too low`, then a transaction dropped by a nonce collision that left `hardhat deploy` waiting forever). | Sepolia deploy | Siroclimb uses only its own keys, kept in `~/.config/siroclimb/sepolia/` (deployer, keeper, bot, player, battery mnemonic). Every Siroclimb contract, the xStock mirrors included, was redeployed from the dedicated deployer `0x6d33…2A5d`. |
| F5 | Right after `setUpdater`, the seeding `pushPrices` reverted on a lagging public RPC node (the role was not visible yet). The FHEVM plugin masked the error as "plugin is not initialized". | Sepolia deploy | The deploy waits until the RPC shows the updater role before seeding. |
| F6 | The Pyth API key is entitled to Equity.US.TSLA/USD; NVDA, AAPL, XAUT and GBP answer 403 "Not entitled". The public Hermes and Benchmarks endpoints now require a key too. | Prices | `/api/pyth` learns the 403s and keeps the entitled feeds. The other markets use the bounded public fallback with reference prices from `/api/prices`. A wider grant switches them to Pyth with no code change. |
| F7 | Yahoo Finance (stocks, GBP) has no CORS, so the browser cannot read it. Stock prices also stop outside US sessions. | Prices | `/api/prices` reads it on the server, with the trading periods. A stock market is open only inside today's pre, regular or post session with a recent candle. Closed markets show *Closed*, and a round never opens on them (the contract skips markets without a checkpoint in the last 60 s). |
| F8 | First browser run: the first faucet claim was still in flight when the balance was first decrypted, so it showed 0.00 and the start button turned into "Get test cUSDC". | Front, Sepolia | `connect()` waits for the first-visit claim before it returns. |
| F9 | Right after a player was funded, the next transaction failed with "insufficient funds" because the public RPC node lagged a block behind. | Front, ops | Those errors are retried, like nonce errors. |
| F10 | Solo starts on fallback markets reverted with `StaleEntry`. The browser first refreshed the checkpoint (one transaction), then sent `startRun`, and by the time the second one landed the checkpoint was more than 30 s old. | Sepolia, front and battery | `startRun` takes a bounded public price that rides along in the same transaction (`try oracle.pushPublic`, same bounds as anyone's push), the entry may be up to 60 s old, and game transactions carry a 0.2 gwei tip. A start is one transaction again. The game was redeployed. |
| F11 | The battery read a run "after" its cash out from a lagging RPC node and saw a zero multiplier handle, which made the unfunded check fail. The on-chain value was right (0.998275 on decryption). | Battery | The battery waits until the run shows as settled with its handles before it decrypts. |
| F12 | With slow inclusion, a 45 s join window was too short for a second player's join (relayer encryption, then a block or two). | Sepolia | The join window is 60 s (deploy parameter). The practice bots start joining 27 s before the bell. |
| F13 | Keeper duties (checkpoints, settlement) and the player's own cash out shared the session key's queue, so a cash out could wait behind a checkpoint transaction. | Front | The autopilot uses a key derived from the session key, with its own nonce queue, and the session tops it up. |
| F14 | Sourcify rejected the redeployed game ("extra_file_input_bug"): the script sent the latest build's compiler input, not the one the deployment was compiled with. | Verification | `scripts/sourcify.ts` sends each deployment's exact `solcInputs/<hash>.json`. Every contract shows a full match. |
| F15 | Battery wave 2: a run's public multipliers no longer matched a recomputation from the oracle. Another checkpoint landed **later in the same block** as the cash out, with the same timestamp, so a recomputation by time counted it while the payout (correctly) had not. The payout was right; the public audit trail was not reproducible. | Contracts, Sepolia battery | Run paths are bounded by checkpoint **indices**: the game stores `exitIndex` (the last checkpoint known at settlement) and `ClimbLadder.multipliers(market, entryIndex, exitIndex, start, cap)` takes indices. A test puts a cash out and a checkpoint in the same block. Ladder and game redeployed. |
| F16 | Battery wave 1: `Panic(50)` reading a run created a block earlier, and balance checks failing because the "after" read still returned the old balance handle. Both came from public RPC nodes lagging behind; the chain was right. | Battery | Reads that follow a write wait until the RPC shows it (`view()` with a condition; balances wait for a new handle). |
| F17 | The browser's practice bots hit the same `Panic(50)` reading the round they were asked to fill, right after the player opened it, so the round ran alone. | Front, Sepolia | The bots retry the read, and `joinRound` polls until the round is visible. |
| F18 | A browser e2e run stopped at "missing revert data" when the session was being granted. The test wallet had 0.02999 ETH, less than the 0.03 ETH grant plus gas, so the node failed the gas estimate without saying why. | Front, Sepolia e2e | The session gets whatever the wallet can spare (at most 0.03 ETH). Below 0.008 ETH the player sees a clear "needs a little Sepolia ETH" message. The browser tests keep a persistent profile per test wallet, so the session and its gas carry over between runs. |
| F19 | Battery wave 1 (final deployment): two balance checks failed on runs whose path was flat (multiplier exactly 1). The "after" read waited for a new balance handle, but the stake debit already counts as a new handle, so a lagging node could serve the state between start and payout. | Battery | Balances are read at exact blocks: the block before `startRun`, and the block of the `RunEnded` event. |
| F20 | Battery rounds: 16 players joining one round at once missed the 60 s join window (`RoundNotJoinable`). Sixteen relayer encryptions started together took more than a minute, so only the opener got in. | Sepolia battery | Battery players encrypt their sides before the round opens, as a player picks a side before clicking. In the browser one encryption takes a few seconds. The finding is documented: a crowd that encrypts at the very last moment can miss the bell. |
| F21 | Right after `closeRound`, a lagging node returned zero score handles and the public decryption failed ("handle 0x00… is not allowed for public decryption"). | Battery, front autopilot | The battery waits until every score handle is non-zero. The browser autopilot already retries on its next tick. |
| F22 | Under load, Yahoo or Hermes requests timed out ("The operation was aborted due to timeout"), and a run started without a fallback price then hit `StaleEntry`. | Battery | Reference prices and Pyth updates are retried, and a failed fetch just means no ride-along price. Battery players start 2 s apart because the relayer is shared. |
| F23 | Battery: three runs left to expire were never settled. The battery's keeper loop had died on a `Panic(50)` from a lagging node, an unhandled rejection that nothing reported, and six players then waited until the watchdog. Settlement is permissionless, so the three runs were settled by hand afterwards with the right payouts. | Battery | The keeper loop catches and logs every error and carries on. Each run has an 8-minute watchdog, and every settled run prints a progress line. |
| F24 | Battery round of 17 players on Sepolia: `closeRound` reverted (it needed ~18.1M gas, over Sepolia's per-transaction cap of 16.78M). After the exits were split out, `finalizeRound` still needed ~19.4M because a flat price made a 16-way tie and every tied player got an encrypted transfer in the same transaction. On the real host every FHE operation and transfer costs about 1M gas, much more than the FHEVM mock suggested (HCU stayed far below its limits). | Contracts, Sepolia battery | Rounds no longer loop over heavy work. `exitAtBell(runId)` exits one run per transaction. `closeRound` only reveals once everyone has exited. `finalizeRound` checks the KMS proof, ranks and records each prize. `claim(runId)` pays one prize (or one refund) per transaction, and anyone may claim for anyone. The autopilot, practice bots, keeper, sweep and battery all follow this pattern. A test covers a 6-way tie paid by claims. Game redeployed. |
| F25 | Consequence of F24 on a previous test deployment: its round 2 (17 battery players, 170 test cUSDC) is closed but can never be finalized or refunded, because both loops exceed the gas cap. Only battery wallets were affected. | Previous deployment | Documented. In the current game no transaction's cost grows with the number of tied players. |
| F26 | Overnight batteries "hung" for hours: the machine running them went to sleep, timers stretched, and the watchdogs fired long after the chain had finished. The chain state was fine (the audit reproduces every path). | Ops | Long runs go through `caffeinate -i`. After a sleep, `sweep.mjs` finishes whatever was left open and `audit.mjs` checks the state. |
| F27 | Many battery and browser glitches (Panic(50) on new arrays, stale run status, old balance handles, `RoundNotOver` just after the bell, receipts never seen by `waitForTransaction`) came from the load-balanced public RPC answering from nodes a block or more behind. | Front, ops | Every read that follows a write now waits for it, receipts are polled directly, and the default RPC is Tenderly's public Sepolia gateway (CORS-enabled, consistent). `?rpc=` overrides it in the front and `RPC_URL` in ops. |
| F28 | Under load, a relayer request (encryption or user decryption) could hang with no answer, which froze a player's screen on "Encrypting…" or stalled a battery player until its watchdog fired. | Front, ops | Every relayer call has a timeout (40 to 60 s) and is retried. |
| F29 | With Tenderly's gateway as the browser's RPC, a busy page (live feed, round polling, autopilot, three practice bots) drew a flood of HTTP 429s. | Front, Sepolia e2e | The browser reads from publicnode again, with every post-write read waiting for the write (F27). Ops keep Tenderly. The round e2e then ran clean: practice bots filled 3 seats, standings sealed, KMS reveal, 2nd of 4, prize claimed. |
| F30 | The "Last round" leaderboard threw "Cannot assign to read only property": ethers returns on-chain struct arrays as read-only `Result` objects, and the code sorted them in place. The sheet kept showing the previous tab. | Front | The results are copied into plain objects before any sort. |
| F31 | With 24 battery players at once, Zama's relayer took over 45 s per user decryption and many requests timed out: about 70 balance and run decryptions in flight together. One browser player decrypts once per run and is not affected. | Ops battery | The battery queues user decryptions (at most 4 at a time, 90 s timeout each, retried). Encryptions and public decryptions are untouched. |
| F32 | Five battery players froze right after encrypting, with no transaction pending. An RPC request had gone unanswered, and ethers waits 5 minutes before giving up, then retries, so each player hit the 15-minute watchdog. | Ops, front | RPC requests time out after 20 s and are retried (`FetchRequest.timeout`), in ops and in the browser. |
| F33 | During the 24-player battery, user decryptions in the battery process timed out again and again, while the same decryption from a fresh process answered in 4 s: the shared relayer SDK instance had wedged after many concurrent requests. | Ops | A fresh SDK instance was not enough, so every battery user decryption now runs in its own short-lived worker process (`ops/decrypt-worker.mjs`, at most 4 at a time). The next battery had no decryption retries. In the browser each player has a single instance and sends one request at a time. |
| F34 | With Tenderly's gateway, the 24-player battery hit "rate limit exceeded" (HTTP 429). ethers retries a 429 up to 12 times with growing back-off, which looked like minutes of silence: players stalled before sending, and one `startRun` landed after its entry price had gone stale. | Ops, front | Back to publicnode for ops too (the post-write waits from F27 cover its lag), and ethers is capped at 3 attempts per rate-limited request. Our senders retry anyway. |
| F35 | Under 24 concurrent players, `eth_estimateGas` for `startRun` (FHE input checks) took more than a minute on the public RPC, again and again. Gas used on Sepolia, measured from receipts: `startRun` up to 3.77M (with the house reserve top-up), `joinRound` 2.99M, `cashOut` 2.21M, `settleRun` 1.88M, `exitAtBell` 1.04M, `closeRound` 3.06M, `finalizeRound` 8.71M for 24 players. | Ops battery | Game calls with a known cost send a fixed gas limit (about 1.5x to 2x the measured peak) and skip the estimate. A call that would revert is still caught by its receipt. |
| F36 | One battery run reported multiplier 0 and payout 0 while the chain said 1. The check had re-read the run's handles from a lagging node instead of reusing the read that had shown them set. | Battery | The handles come from the read that passed the wait. |
| F37 | Key hygiene: the first deployments and batteries used keys from another project's folder, and the mirrors' creator was the shared deployer. | Ops, contracts | Everything moved to Siroclimb's own keys (F4), with a full redeploy and a new battery. The repo has no path to the other project's keys; only the Pyth API key is shared. |
| F38 | New deployment, wave 1: two starts on stock markets reverted with `StaleEntry`. Under load the reference price lookup timed out, so no fallback price rode along; separately, the browser re-decrypted the balance from a lagging node right after a payout and showed the pre-payout amount. | Battery, front | The battery retries the price lookup and resends a start that reverted for lack of a fresh entry. The front decrypts the balance as of the payout or claim block (`blockTag`), which is exact even on a lagging node. |
| F39 | Battery, 24-player round on the new deployment: one winner's prize was not claimed by the battery, because a lagging node answered `prizeOf = 0`. Its balance check failed, and the sweep claimed the prize afterwards (the pot was fully paid). | Battery | Prizes are read as of the finalize block. |

## Browser end to end (real front, Sepolia, injected test wallet)

| Flow | Result |
| --- | --- |
| Solo (`tests/chain/solo.mjs`) | Connect: two wallet transactions (operator approval, session grant), then the first-visit faucet. Balance decrypted (one EIP-712 grant). The run starts in one transaction (side and stake encrypted, entry price riding along), the cash out is paid as an encrypted transfer, and the decrypted balance moves by exactly the payout. 0 console errors. |
| Round (`tests/chain/round.mjs`) | Practice bots took 3 seats with their own encrypted sides, and every other player showed *Sealed* while live. The browser's autopilot exited the runs at the bell, closed the round, got the KMS reveal and finalized. The player came 2nd of 4, the prize was claimed, and the leaderboard showed the round. Nothing ran on our side. |

## On-chain battery (Sepolia, current deployment)

`ops/battery.mjs 24 2 2` on `Siroclimb` `0xf280…DE8c`: 24 players from Siroclimb's own mnemonic
plus one unfunded wallet, two solo waves, two full rounds. Every settled solo run is checked end to
end: the public multipliers match `ClimbLadder` recomputed between the recorded checkpoints, the
decrypted multiplier is the one of the player's side, `paid` and the payout are exact, and the
player's decrypted cUSDC balance at the exact blocks moved by `paid x mult - paid`.

| Metric | Result |
| --- | --- |
| Solo runs | 48 / 55 passed every check. No run that settled failed a check. Of the 7 others, 2 starts reverted with `StaleEntry` (fixed in F38) and 5 ran past the watchdog under RPC and relayer load. |
| Scenarios | Early cash outs, runs left to expire and settled by a third party, stakes above the 100 cap (clamped on ciphertexts), an unfunded player (moves 0, paid 0), packed runs (capped path picked on ciphertexts), published runs (multiplier revealed with a KMS proof) |
| Round 0 (TSLAx) | 24 players (23 funded plus 1 unfunded), pot 230 cUSDC, an 11-way tie for 2nd shares its places. All 24 checks pass: decrypted score equals the side's multiplier, rank and prize match a local recomputation, and the balance moved by `prize - entry` |
| Round 1 (NVDAx) | 24 players, a flat price so everyone tied (pot split 24 ways, paid by 24 claims). 23 / 24 checks; the last prize was left unclaimed by the battery (F39) and claimed by the sweep |
| After the run | `audit.mjs`: 92 / 92 settled runs reproduced from public chain data, 2 / 2 pots fully paid. `sweep.mjs`: nothing left open |
| Sepolia ETH | 0.85 ETH from the Siroclimb deployer (0.02 per player plus gas) |

Measured gas on Sepolia (F35): `startRun` up to 3.77M, `joinRound` 2.99M, `cashOut` 2.21M,
`settleRun` 1.88M, `exitAtBell` 1.04M, `closeRound` 3.06M, `finalizeRound` 8.71M for 24 players.

Previous deployment (retired, same contracts before the key move): 249 runs settled, every path
reproduced, and 4 rounds, two of them with 24 players, finalized with every pot paid.

Raw results: `ops/battery-results/`.
